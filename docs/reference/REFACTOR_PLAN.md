# SLSFlow — план рефакторингу в компонентно-плагінну архітектуру

База: чиста `slsflow-main` @ v0.91.0. Ціль (з транскрипту): скелет + реєстр + точки
розширення; самореєстрація на імпорті; **explicit** перелік плагінів; пропрієтарне в
окремому модулі. Розділення тоді = «який плагін у переліку», не хірургія.

## Принципи виконання

1. **Архітектура спершу, split потім.** Робимо самореєстрацію в наявному монорепі (нічого
   не ділимо). Коли компонентне — розділення стає організацією переліків плагінів.
2. **Інкрементально + поведінку зберігаємо + тести зелені на кожному кроці.** Кожна стадія
   проганяє всі сьюти. Бо код Клодом писаний — без цього ризик незмінно.
3. **Прив'язка до фаз релізу:** Phase 1 (бекенд) — передумова v0.2; Phase 3 (UI) —
   передумова v0.3; SDK майже готовий.
4. **Explicit реєстрація** (явний перелік модулів), не неявний обхід.

## Phase 1 — Реєстр раутів бекенду (console_api)

*Еталонний патерн для всього іншого. Передумова розділення v0.2. Обсяг: середній, ризик: низький.*

Зараз: `main.py` тримає літеральний `ROUTES = {(method, path): (handler, param), ...}` (50+
записів) + статичний `from routes import (...)`. Сигнатури вже у формі `(handler, param_key)`,
де `param_key ∈ {None, 'name', 'id', ...}` — тривіально лягає в декоратор.

**Стадія 1a — реєстр + декоратор, без зміни поведінки.**
- Новий `routing.py`: реєстр + декоратор:
  ```python
  @route("GET", "/api/pipelines")               # param=None
  @route("GET", "/api/pipeline-status", param="name")
  ```
- Імпорт модуля → декоратор вставляє `(handler, param)` у реєстр.
- **Перевірка:** після імпорту всіх route-модулів реєстр відтворює поточний `ROUTES`
  **байт-в-байт**. `assert registry == ROUTES`. Усі бекенд-тести зелені.
- Поки що паралельно зі старим `ROUTES` — нічого не ламаємо.

**Стадія 1b — перевести 14 модулів на самореєстрацію; `main.py` → ранер.**
- `@route(...)` на кожен хендлер у `routes/*.py`.
- Прибрати літеральний `ROUTES` із `main.py`; прибрати barrel-імпорт.
- `main.py` стає ранером: **явний перелік** route-модулів → реєстр наповнюється → диспетч
  із реєстру (логіка `param_key` зберігається — реєстр тримає той самий tuple).
- **Перевірка:** ті самі раути резолвляться, та сама поведінка; усі бекенд-тести зелені
  (`test_templates.py`, що перевіряв `ROUTES`, тепер перевіряє реєстр).

**Результат:** додати/перенести раут = торкнутись його модуля, не `main.py`. Лямбда=ранер.

## Phase 2 — Реєстр адаптерів SDK *(опційно, малий)*

*Вирівнює SDK під патерн «іменованих адаптерів». Не на критичному шляху розділення.*

Зараз: `from . import pyarrow_, pydantic_, glue` (фіксовано).

- Реєстр + `@adapter("glue")`; резолвер за іменем; `Asset.from_*` зберігається.
- **Перевірка:** усі SDK-тести зелені, `Asset.from_pyarrow/pydantic/glue` працюють як раніше.
- Можна вставити будь-коли; пропрієтарного адаптера зараз нема, тож суто «під патерн».

## Phase 3 — Точки розширення UI *(найбільше, наостанок)*

*Передумова розділення v0.3. Обсяг: великий, ризик: високий — семи нема взагалі.*

Зараз: сторінки = файли (`app/*/page.tsx`), навігація захардкоджена, нема куди вставити.

**Стадія 3a — інфра реєстрів:** `routeRegistry`, `navRegistry`, `sidebarRegistry`.
**Стадія 3b — перевести фічі на реєстрацію:** кожен feature-модуль реєструє сторінку + нав.
**Стадія 3c — реєстро-кероване роутування:** або замінити Next-файлове роутування на
кероване реєстром, або лишити файли, а показ/реєстрацію гейтити explicit-маніфестом.
- **Перевірка:** шелл рендериться з реєстрів; з повним маніфестом UI ідентичний поточному;
  усі vitest-тести зелені.
- Розбити на дрібніші підстадії при виконанні — це найризикованіша частина.

## Phase 4 — Розділення OSS / пропрієтарне *(після компонентизації, тривіально)*

Робиться по шару, щойно той шар компонентний:
- Створити пропрієтарний модуль (окрема директорія/пакет, контроль доступу).
- Перенести пропрієтарні плагіни туди: Team/Enterprise route-модулі, Team UI-фічі, `ai`.
- **Explicit переліки:** OSS-білд = скелет + OSS-плагіни; пропрієтарний = + пропрієтарні.
- Нічого не вирізаємо — просто не включаємо пропрієтарний модуль у перелік.

Перенести фічу між тарифами = перенести її плагін-модуль між OSS- і пропрієтарним переліком.
